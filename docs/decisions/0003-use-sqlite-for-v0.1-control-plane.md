# 0003：v0.1 Control Plane 使用 SQLite 单写进程

- 状态：已接受
- 日期：2026-08-21

## 背景

Control Plane 必须原子保存 Task、Approval、Run、RoleRun、状态历史和命令幂等结果，并在进程中断后恢复。v0.1 需要先证明一条本地、可测试的设计到交付闭环，不需要多节点调度、跨区域高可用或大规模并发。

README 将 PostgreSQL 作为完整系统事务数据的默认候选，但在尚未验证状态模型之前引入独立数据库服务、连接池和部署拓扑会扩大首个闭环。纯内存或 JSON 文件又无法可靠提供外键、唯一约束、原子多记录更新和崩溃恢复。

## 决定

- v0.1 的 Control Plane 使用 Node.js 内置 `node:sqlite` 和文件型 SQLite 数据库；测试可以使用临时文件或内存数据库。
- 生产式试跑使用 Node.js 24 LTS，并锁定经过契约测试的最低补丁版本。`node:sqlite` 仍处于 release candidate 状态，因此 Node 升级必须重新运行数据库契约和恢复测试。
- v0.1 只允许一个 Control Plane 写进程。SQLite 开启 foreign keys、WAL、defensive mode 和 busy timeout；写命令使用短事务，不在事务内调用 Agent、网络、Git 或其他外部工具。
- Schema 通过前向迁移建立，迁移具有版本、摘要和原子应用记录。已应用迁移不得原地修改。
- 当前状态和追加式历史使用普通关系表保存；不可变 JSON 制品保存规范内容和 SHA-256。数据库约束承担单活动 Run、单活动 RoleRun、引用完整性和关键状态字段组合约束。
- 所有命令通过 Command ID、请求摘要和持久化结果实现幂等，通过聚合版本实现乐观并发；RoleRun 另使用 fencing token 隔离旧 Worker。
- 事务提交后的外部工作使用 outbox 和明确 Operation ID 衔接。进程恢复只读取数据库事实，不依赖 Pi Session 或聊天记录。

## 影响

- v0.1 可以无额外数据库服务运行并真实测试崩溃恢复、事务和约束，而不是用内存 mock 证明持久化。
- 同步 SQLite API 会占用 Control Plane 事件循环，因此数据库操作必须小而有界；模型运行和工具执行不占用事务。
- 单写进程是明确限制，不允许把同一个数据库文件放到网络文件系统或由多个服务实例同时调度。
- 后续迁移到 PostgreSQL 时必须保留端口契约、状态不变量、幂等键和事务语义，不能把 SQLite SQL 细节暴露给编排层。
- `node:sqlite` 的稳定性和 Node 补丁版本属于运行清单中的环境引用及升级门禁。

## 未采用的方案

- **直接使用 PostgreSQL**：长期更适合多实例和生产运行，但对 v0.1 的本地闭环增加部署与测试成本；待真实场景验证状态模型后再决定。
- **JSON、Markdown 或 Pi Session 作为状态存储**：无法提供需要的事务、约束和幂等恢复语义。
- **第三方原生 SQLite 驱动**：成熟度较高，但会增加原生构建、供应链和跨平台发布面；v0.1 优先使用 Node 自带模块并以契约测试控制风险。
- **完整事件溯源**：当前记录加追加 Transition 已满足解释和恢复，事件重放会增加投影、迁移和一致性复杂度。
